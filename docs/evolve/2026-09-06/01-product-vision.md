## 1. 这轮解决的具体问题

参考图片指出的问题是：当人与 Agent 之间需要不断传递需求、实现结果、反馈和补充说明时，人会被迫判断“对方写完没有”“现在是否该再次启动 Agent”“上一次读到的是否还是最新版本”。交互次数越多，人的调度负担越大。

CLI 本身不是问题。需要消除的是由人反复执行的拉取、唤醒、等待和转述。后台程序可以使用轮询或事件机制，前台的人应该只需要看得见目标、当前依据、下一步提案和最终结果。

本轮的产品取舍：用 Doc Free 的在线文档承载协作，用 Active Agent 持续观察和推进。所有新界面位于 `/workbench`，不加入聊天窗口、群组、联系人或 IM 网关。

## 2. “文档就是载体”的工程含义

“文档”是有标题、地址、可读正文、版本和共同编辑能力的协作对象，不能退化为一个只有开发者能找到的 Markdown 文件路径。

- **人眼可见**：目标、依据、提案和结果都能在工作台中打开；不需要查看数据库才能知道 Agent 在干什么。
- **Agent 可见**：机器通过同一份文档的 REST/MCP 表示读取目标和上下文，不维护一套用户无法看见的独立任务语义。
- **可恢复**：重新启动 worker 后，从文档重建任务进度。删除操作性 checkpoint 不会删除任务约定和已发布结论。
- **可带走**：文档可以导出 Markdown，包括可机器读取的契约块；不要求导出某个 Agent 的私有记忆才能解释结果。

物理存储仍然必要：Yjs 保存协作状态，Doc Free JSON 保存可读投影和事件，SQLite 保存调度检查点。关键区别是：这些是保存和执行机制，协作的语义载体仍是双方共享的文档。不能把“文档载体”误写成“完全不用存储”。

## 3. 最小可用的产品闭环

1. 人创建、编辑一份来源文档。
2. 人为该文档写下一个持续目标，系统生成普通的任务文档。
3. Worker 持续观察文档。编辑不断发生时延长等待；编辑安静后再请求模型。
4. 模型决定继续观察、指出缺失信息或生成修改提案。
5. 提案是一份可打开的文档，包含来源版本、精确引用、理由和完整修改前后内容。
6. 人接受或拒绝。接受时重新验证任务和 CRDT 正文，过期提案不得覆盖新内容。
7. 处理结果写回提案文档，成为下一轮双方都能看见的依据。

这套交互让人不必一遍遍启动模型。人工审阅仍然是 0.2 写回正文的默认边界；自动运行不等于自动接受所有修改。

## 4. 人与 Agent 的协作关系

| 能力 | 人 | Agent / MCP 客户端 |
|---|---|---|
| 查看正文与历史任务 | 工作台 | REST / MCP |
| 修改正文 | 在线 CRDT 编辑器 | 带版本检查的文档写接口 |
| 创建持续目标 | 目标表单或任务原文 | `active_doc_assign` |
| 暂停、继续、完成 | 工作台 / 任务约定 | `active_doc_status` |
| 查看依据与提案 | 工作台和原文 | 同一文档协议 |
| 明确接受、拒绝 | 审阅按钮 | `active_doc_review` |

这里的同权是同一协作对象、同一协议和可追溯的行为。当前共享令牌不是严格身份系统，显示名称也不证明真实身份。内置 worker 只发布提案，不调用审阅接口；其他持有令牌的客户端拥有工作空间能力。这一限制在安全文档中明示。

## 5. 第一批真正适合的场景

- 把持续变化的产品需求转成可验证的验收条件。
- 审核方案是否缺少依赖、前置条件和失败恢复步骤。
- 对在线研究笔记给出有来源的整理和缺口提示。
- 根据同一份规范持续审校指定章节。

当前不宣称自动执行代码、真实部署、外部调查或企业流程审批。模型只能基于这份来源文档提出文字修改，不能假装已经完成外部验证。

## 6. 面向大型开源项目的定位

一句话定位：**A proactive collaborator for your living documents.**

差异化需要由读者五分钟内可以复现的行为支持：写目标、等提案、看依据、继续编辑、观察旧提案被保护性拒绝。单纯增加更多模型、工具或 Agent 数量不会自动改善这一体验。

100k stars 是愿景，不是可承诺的交付指标。当前更可靠的目标是：首次成功容易、任务行为可解释、协作修改不丢、错误可恢复、项目可自托管、贡献者能够快速理解边界。具体验收门槛见路线图。
