## 合并转发与原生协议

当前合并入口按会话声明的 `native_features.message_forward_bundles` 显示。从多选栏进入后，使用所选消息 ID 读取来源，选择接收会话，填写附言和原生提及，提交合并请求。真实回执返回前保留原选择；取消不等于发送成功。

当前服务端协议为：

| 动作 | HTTP 接口 | MCP |
| --- | --- | --- |
| 合并分享 | `POST /rooms/:rid/messages/forward-bundle` | `im_forward_bundle` |
| 展开已分享记录 | `GET /rooms/:rid/messages/:mid/forward-bundle` | `im_read_forward_bundle` |
| 按原请求恢复本人回执 | `GET /rooms/:rid/messages/forward-bundle-receipts?client_id=...` | `im_forward_bundle_receipts` |

当前请求限制为 1–50 条不同来源和 1–20 个不同目标会话。来源快照由服务器生成，包含分享时的版本、作者、时间、正文和附件信息；提交方不能上传伪造的展开内容。每个目标产生一条真实合并消息卡片，附言是卡片消息自己的正文。目标成员按实际收到的分享副本读取，不需要伪装成原群成员。

当前源码同时核对来源版本、撤回、本人隐藏、转发保护、源与目标成员资格、提及对象及附件配额；稳定 `client_id` 标识整个批次。回包不明时先恢复原回执，不自动生成新的请求标识后再发一批。组件测试已验证关闭再打开面板恢复原意图；待确认意图在当前 OfficeState 生命周期中保存，应用进程退出后的持久恢复尚未实现。

Human 与 Agent 使用同一原生接口与会话授权。本轮真实 MCP 实际调用了 Agent 合并转发与嵌套转发，A2A 实际调用了共享记录展开和缓存回执读取；结果与撤权边界见下一节。没有用工具声明存在代替真实通信检查。

「创建群聊并转发」、全部飞书转发搜索/快捷应用路径和五端完整交互不能从这些入口推断完成，冻结时按真实结果列出尚存差距。
