## 下一批的两个具体修补点

### 1. 桌面会话摘要直接显示 `:feishu:SMILE:`

**证据：步骤 1。** 左侧会话列表第三条摘要中，可见 `:feishu:SMILE:` 原始字符串。用户在消息列表扫描最近内容时，需要自行理解存储编码；这与消息正文及顶部预览已采用经典表情呈现的行为不一致。

**建议：** 摘要复用已有经典表情解析，或在紧凑文本布局中使用可读的表情名称；未知 token 仍按既有兼容规则保留。保留摘要的一行省略，不把完整 token 长度算成可读的消息内容。

**下一轮验收：** 在包含一条已知经典表情的会话中，更新消息后查看桌面会话摘要；已知 ID 显示对应图片或可读名称，普通文本、未读角标和摘要省略保持可用。应同时查看移动消息列表，但本次指定的 iOS 截图是聊天页，没有对应移动摘要证据。

### 2. 加急默认视口没有完整呈现渠道区，滚动提示不足

**证据：步骤 2、4。** Mac 1079 × 739 的窗口截图中，弹窗默认状态只露出“仅应用内”和“应用内 + 短信”，电话项尚在下方。iOS 395 × 850 的模拟器截图中，“应用内 + 电话”标题已露出，但说明只显示了一部分。两张图均为两个候选成员、已选一位 Agent、键盘未显示的状态。

**这是可滚动内容与固定操作区之间的可发现性问题，不能简单称为布局溢出。** 成员和渠道位于可滚动正文，取消/发送位于固定底部操作区；截图没有证明电话项无法滚动到达，也没有证明发送按钮遮住了可达的内容。固定按钮在两端均完整可见。已知功能约束仍是只有应用内可发送，短信与电话未配置且禁用。

**影响：** 初次打开时，桌面用户可能以为只有两个发送方式；手机用户尚不能完整读到电话渠道为什么不可用。当前截图也没有一个清楚的滚动提示告诉用户还有选项或说明在下方。

**建议：** 在保留固定主动作的前提下，收紧渠道说明的默认排布，或提供明确的滚动提示；不因为要展示完整而把未配置渠道变成可选。最终紧凑程度需要补真实飞书相同状态参考后再确定，不能从本报告推导任意重设计。

**下一轮验收：** 使用同一来源消息、两个候选成员、已选一位 Agent、无软键盘，重现上述两个捕获尺寸；先记录打开后的默认状态，再正常滚动至底部，确认三种渠道及最后一条不可用说明均可完整阅读、固定按钮不覆盖滚动终点。然后单独检查软键盘打开和更多成员的情况，不能以当前两成员截图替代这些状态。
