## 1. Agent 终态自动归档

业务工作流先由 Terminal Activity 持久记录终态，成功后才调用 Archive Activity。结果和归档状态分别存储；业务失败或取消仍能查询归档结果。Terminal 写入失败则明确跳过归档。

插件通过部署环境 `RENJI_RUN_ARCHIVE_CONFIG` 装配，配置是服务器持有的 0600 文件。工作流输入只有 Run ID，不能指定目标 URL、凭据、群聊或正文。没有配置会明确报告 disabled，不虚报已归档。当前适配器仍受限于已经批准的单来源合成空间；生产多来源权限同步尚未闭合。

已知外部文档 ID 的读回故障最多重试三次；没有外部 ID 的未知创建结果禁止重建。租约冲突等 125 秒后再尝试，整体上限 11 分钟。旧 Temporal 历史用版本标记保持兼容，重放不会补发新动作。

独立审查发现并修复了“停止发生在终态记录之前”的竞态。当前 Run 已停止时，可以凭数据库生成的同 Run 停止事实归档，执行器原本提交的失败或完成报告仍保持原样；不为迎合归档判定制造第二条执行器事件。其他状态仍要求匹配实际终态事件。

真实服务上运行了两次独立的既有 Run 对账，最终二进制的验收工作流为 `renji-archive-case2-20260909-0620-final`。它的 11 个历史事件中只有一次 Archive Activity，没有 Planner、Execute 或 Terminal Activity。返回原归档 `75ae64e9-7234-4293-8b15-8cbfb70faefb`、原 doc_free 文档 `9d62380a`，状态 verified。前后完整读取结果相同：原 Run 仍 failed，证据仍 5 条，业务动作仍 0，原 4 份文档全部不变，原文档创建累计次数仍为 1。

这证明了真实既有执行档案的持久对账，不代表成功模型执行的自动归档已经完成真实验收。自动业务链、取消、停止竞态、125 秒等待与旧历史重放另有本地 Temporal SDK、真实独立 PostgreSQL schema 的测试证据。

## 2. 文档先让人读懂，再保留完整证据

新创建档案使用 `renji-run-markdown-v2`。开头展示任务目标原文预览、Run 实际状态、创建时间、已提交消息动作数量、融云运输状态和阶段输入尝试数，后面完整保留原始 JSON 和校验值。目标预览有长度限制和安全围栏，不能通过目标文字伪造标题或执行结论。

模型报告不计为动作成功；阶段输入记录不代表模型已返回。只有服务端动作账本及一致的真实回执才计入已提交消息。运输按每个任务的最新记录统计，融云已受理不代表成员设备已收到或成员已读。

升级渲染器不会重建已经冻结的同一 Run、证据游标和目标档案；原 ID、正文、标题、hash 和渲染器版本保持原样。新游标才使用新渲染器。真实 `9d62380a` 因此仍是 v1，未为了展示新摘要而改写历史。新摘要生成和跨版本复用已通过单元与真实 PG 验证，尚未向该历史文档发布 v2 改写。
